# Design: Per-camera notification cooldown with quiet in-place updates (issue #672)

## Problem Statement

One real-world event on one camera produces several near-identical pushes inside a minute or
two. Reported by @andymcmanus in #672 on battery Ring cameras via ring-mqtt: a neighbour
walking a dog produced three pushes in about a minute (front_door twice, side once); a visitor
lingering at the door produces repeated pushes from that camera. Each motion re-trigger opens a
new event window, so one happening becomes several analysed events.

The issue says caption dedup "never suppresses real subjects". That is not what the code does.
`_is_caption_novel` (`core/video_analyzer.py:1701-1730`) suppresses a real-subject caption when
it scores at or above 0.85 against a match under 30 minutes old. The bursts most likely pass
because the model words the same scene differently and the score lands below 0.85. This is an
inference from the code; it has not been confirmed from the reporter's debug logs.

His workaround analysis is correct: `_send_notification` (`video_analyzer.py:1507`) pushes
straight to the configured notify service, so no Home Assistant automation can sit in front of it.

## What Makes This Cool

The phone buzzes once per camera per window and shows one card that stays current while the
subject is there, instead of a stack of near-duplicates. Every analysed event still reaches the
phone: inside a window, a later event replaces that window's card with the latest caption and
image. Earlier captions inside the window are overwritten on the phone; they remain in the
stored analysis.

## Constraints

- Opt-in. Default 0 must produce today's payload and today's non-blocking call, unchanged.
- Gates only the outbound push. Analysis, `sensor.*_recognized_people`, `hga_last_event_frame`,
  the latest-image signal and vector storage are unchanged.
- Independent state per camera. An event on another camera is never affected.
- Enhancement, not a fix for something broken in the wild: bundles into the monthly release
  (RELEASING.md), with a `## [Unreleased]` CHANGELOG entry and README update.
- Quiet replacement is a Home Assistant companion-app behaviour. It is best effort and differs
  between iOS and Android.

## Premises

Agreed with Lindo on 2026-10-02:

1. The burst problem is real; the fix belongs at the notify gate, not in the dedup threshold.
2. A time-only cooldown can hide a different subject arriving inside the window, so it needs a
   bypass rather than being blind.
3. Per-camera scope is fine for v1, even though the reporter's cross-camera example only drops
   from three pushes to two.
4. Opt-in, default 0, ships in the monthly bundle.

## Cross-Model Perspective

Codex (gpt-6-astra, high effort, read-only cold read) on 2026-10-02. Close paraphrase.

- Coolest version: one evolving "visit" card ("Visitor at front door" then "left a package" then
  "departed, 3 observations"), later correlated across cameras, optionally shown through the
  companion app's `live_update`. Out of scope for v1; recorded under Open Questions.
- Fragile assumption: that "same tag plus quiet flags" guarantees a quiet replacement.
  On Android, `alert_once: true` only suppresses re-alerting while the notification is still
  showing; if the user dismissed it, the update can alert again. On iOS, `tag` replaces, and
  quiet delivery needs `push.interruption-level: passive`; `sound: none` alone is not enough.
  Other `notify.*` services have no replace or quiet contract at all. So this is best-effort
  alert coalescing, not a guaranteed cooldown.
- Existing 50%: `sentinel/notifier.py` already has cooldown state, tags and iOS interruption
  levels. Reuse the payload conventions, not the policy (Sentinel drops and batches).
- Verified against the code and carried into the Recommended Approach: `_finalize`
  (`video_analyzer.py:1448-1449`) awaits notification handling before storage, so an exception
  in the new path would skip storage; `_SUBJECT_RE` returns presence, not classes; recognition
  data should come from the same batch rather than `_last_recognized` read after an await.

## Approaches Considered

- A, cooldown with new-subject bypass that drops pushes inside the window: ruled out, it
  discards alerts.
- B, A plus quiet in-place update: chosen.
- C, an analyze-only mode plus an event so users throttle in their own automations: ruled out,
  it hands the work to every user.

## Recommended Approach

New option `video_analyzer_notification_cooldown_s` in Global Options, defined in `const.py`.
Integer seconds, range 0 to 3600, default 0, number selector so negative input is rejected.
The options flow is `OptionsFlowWithReload`, so any option change (cooldown value, notify
target) reloads the entry and the in-memory window state starts empty. No explicit clearing
code is needed beyond that.

**Applies only to companion-app targets.** The cooldown is active when the resolved service
name starts with `mobile_app_`. That covers the options picker and the
`discover_mobile_notify_service` fallback. Any other `notify.*` target (hand-edited config, a
notify group) is sent exactly as today, with one INFO log per entry load saying the cooldown
does not apply. Nothing is dropped in either case.

**State, per camera entity id.** Window start (monotonic), a window id (wall-clock epoch
seconds at window start), and the window's human level: `none`, `known` or `unidentified`.
A per-camera `asyncio.Lock` covers the read of this state, the dispatch and the commit, so two
batches for one camera cannot both see "no open window" whichever caller of
`_analyze_and_finalize` they come from.

**Human level of a batch.** Two signals, both already available:
- Face recognition names for this batch, passed down from `_analyze_and_finalize` through
  `_finalize` and `_handle_notification` as a parameter. The helper does not read
  `self._last_recognized`. "Indeterminate" is ignored.
- Human presence in the caption: the existing `_caption_mentions_person` helper
  (`video_analyzer.py:424`), the same detector the notify-frame picker uses. Amended by
  eng-review decision R1; the original text named an 8-term subset of `_SUBJECT_RE`.

| Batch contains | Level |
|---|---|
| "Unknown Person" from face recognition | `unidentified` |
| Enrolled names only | `known` |
| A caption human with no face result | `unidentified`, except inside a window already at `known`, where it leaves the level at `known` |
| Neither | `none` |

The exception in the third row was decided by Lindo on 2026-10-02 after the final review round:
a recognized resident who turns away from the camera produces a caption human with no face,
and that must not sound a second time. From a `known` window, only an explicit
"Unknown Person" result escalates.

The order is `none` < `known` < `unidentified`. Vehicles, animals and packages are not
classified and never trigger a bypass. This is deliberate: caption wording varies between
analyses of the same scene, and "a person walks past" followed by "a person with a dog" must
not re-alert.

**Decision for a push that passed the existing novelty check:**

| Situation | Dispatch | Effect on state after a successful dispatch |
|---|---|---|
| No open window, or window expired | Alerting | New window: new start, new id, level set from this batch |
| Open window, batch level higher than the window's level | Alerting (bypass) | Start and id restart; window level raised to the batch level |
| Anything else inside the window | Quiet update | None |

So the bypass fires only when the scene escalates: a human appears where there was none, or an
unidentified person appears where only enrolled people had been seen. A window can alert at
most three times (open, then `known`, then `unidentified`), and a level never goes back down,
so alternating subjects cannot flap. One subject whose face evidence improves between batches
(caption human, then "Unknown Person", then an enrolled name) stays at `unidentified` and does
not re-alert. Quiet updates never extend the window. The fail direction for an unclassifiable
caption is a quiet update: the card still changes to the new caption and image, without sound.

**Payload.** Message, title and image unchanged. Tag is per window, so a new window or a bypass
creates a new card and older cards stay in the tray as they do today.

| Dispatch | Extra fields under `data` | Call |
|---|---|---|
| Alerting | `tag: hga_camera_<camera_name>_<window id>` | `blocking=True` under a 10 s timeout |
| Quiet update | same `tag`, `alert_once: true`, `push: {interruption-level: passive, sound: none}` | `blocking=False` as today |

This follows `sentinel/notifier.py:363-365` and `:495-496`. The blocking call can hold that
camera's pipeline for up to 10 s per alerting push when the notify service hangs; accepted,
since alerting pushes are at most three per window.

**Failure handling.** What this code can observe is: no notify service found (today's WARNING
and early return, which the helper now reports as a failure), a schema error, a timeout, or an
exception raised by the notify service while the blocking call runs. On any of those for an
alerting or bypass dispatch, no state changes at all: start, id and level stay as they were, so
the next batch alerts again. Delivery to the handset is not observable and is not claimed. The
new dispatch helper is wrapped in `except Exception` with a WARNING log so `_store_results`
always runs after it; `asyncio.CancelledError` propagates so unload still cancels workers. The
pre-existing risk that `publish_latest_atomic` or `_is_caption_novel` raises and skips storage
is out of scope here and goes to TODOS.md.

**Known limits, documented in the README and summarized in the option's description text.**
- Works only when the notify target is a single companion-app service (`notify.mobile_app_*`).
  With a notify group or any other target the option has no effect.
- A vehicle, animal or package arriving inside an open window is a quiet update.
- A second enrolled person arriving inside a window is a quiet update.
- Two different unidentified people inside one window: the second is a quiet update.
- A stranger arriving while a recognized resident is in the window (level `known`) alerts only
  when face recognition returns "Unknown Person" for the stranger. A stranger whose face is
  not detected is a quiet update. If the resident was never recognized, the window is already
  `unidentified` and the stranger is a quiet update even with a detected face.
- Caption human detection uses English terms. With another VLM response language, the human
  bypass depends on face recognition alone.
- Android: if the user dismissed the card, a quiet update can sound again. Accepted for v1:
  the user cleared the card and the scene is still active.

## Success Criteria

- Option at 0: payload and call identical to today (asserted in a test).
- One unchanged subject on one camera (the lingering visitor, the dog walker), option at N:
  exactly one sounding push in the N seconds after the first. A second sounding push from that
  camera in that period, with no escalation in human level, is a failure. On Android this is
  judged while the card is still showing; a re-alert after dismissal is the documented limit.
- Later events in that period replace the same card with the new caption and image.
- An escalation (`none` to a human, `known` to `unidentified`) inside the window alerts.
- Sensors, events, latest image and stored analysis are unchanged for every analysed batch.
- A failed alerting dispatch does not skip storage and changes no window state.
- @andymcmanus confirms the first criterion on his setup for both of his cases.

### R3-1 — feasibility

**Problem**

> The level table makes a batch with a caption human and no enrolled name 'unidentified', and 'unidentified' is above 'known'. Face detection is intermittent, so one enrolled person can produce a false escalation: batch 1 recognizes the resident (window level 'known'), batch 2 shows the same resident turned away with no face hit (caption human, no enrolled name, level 'unidentified'), and the bypass row sends a second sounding push. The document only covers face evidence that improves between batches ('caption human, then Unknown Person, then an enrolled name ... does not re-alert'); it does not cover evidence that degrades. The result is two sounding pushes for one unchanged subject, which the success criterion calls a failure unless the level escalated, and here the escalation is an artifact of a missed face. The test list in Next Step 5 has no case for an enrolled name followed by a no-face caption human.

**Remedy**

> Decide how a caption human with no face hit is treated inside a window whose level is 'known': either it does not raise the level (only an explicit 'Unknown Person' result escalates from 'known'), or the extra alert is accepted and added to the Known limits. Add a test for the sequence enrolled name, then caption human with no face, on one subject.

### R3-2 — consistency

**Problem**

> The Known limit 'A stranger arriving while a resident is in the window alerts only if face recognition is on and detects the stranger's face. Otherwise it is a quiet update' disagrees with the level table in both directions. (a) A later batch that shows only the stranger, with no face hit and no enrolled name, is 'a caption human with no enrolled name', so its level is 'unidentified' and it alerts in a 'known' window without any face detection. (b) If the resident's own first batch had no face hit, the window is already 'unidentified', and a stranger whose face is detected as 'Unknown Person' is a quiet update, although the limit says that case alerts. The test 'resident then stranger alerts' in Next Step 5 does not say which of these conditions it asserts.

**Remedy**

> Rewrite the limit so it matches the level table (or the table as changed by R3-1): state that the stranger alerts only when the window level is 'known' and the stranger's batch reaches 'unidentified', and name the case where the resident was not recognized and the window is already 'unidentified'. State the exact conditions of the 'resident then stranger alerts' test and add the quiet counterpart.

### R3-3 — clarity

**Problem**

> Next Step 1 gates coding on a phone test on Lindo's phone, but the decision rules have no rule for an Android quiet update that sounds or shows a heads-up banner while the card is still showing. The only rules are for an iOS quiet update that sounds, an image that does not refresh, and an Android re-alert after dismissal. If Lindo's phone is Android, a failure of the main quiet-update behaviour has no stated outcome, and the same gap applies when the reporter checks Android on the pre-release 'with the same rules'.

**Remedy**

> Add a decision rule for Android: if a quiet update sounds, vibrates or shows a heads-up banner while the card is still showing, change the quiet payload before coding (or before the bundle when found on the pre-release).

D4 — Fix the sensor-names race in this PR?

## Changes from the pre-landing review (/ship, 2026-10-02)

Six reviewers (testing, maintainability, security, performance, simplification, red team) read
the first implementation. Four findings changed the design; Lindo decided each. These override
the ledger and the Amendments above.

1. **No awaited push, no fallback timer (reverses the blocking send and R7).** Home Assistant's
   `notify.mobile_app_*` service catches push failures and only logs them, so an awaited call
   returned normally on a failed push and the window opened anyway. The wait also held the
   camera's worker and, on a timeout, cancelled the push without re-sending it. Sounding pushes
   are now sent exactly like today's (non-blocking) plus a tag. A window is not opened only
   when the service call raises immediately. Limit documented: delivery cannot be confirmed.
2. **Face-confirmed unknown always sounds once per window, and the negation scrub is wider.**
   `_caption_mentions_person` read "no visible people", "without any people", "not a person in
   sight" and "empty of people" as a human, which put a window at `unidentified` and silenced a
   later "Unknown Person" face result. The window now tracks whether an unknown person was
   confirmed by face recognition; the first such result in a window sounds. `_NEGATED_PERSON_RE`
   covers the listed phrasings. Cost: one stranger can sound twice (caption, then face).
3. **Stale-update rule removed (reverses R6).** Ring event-recording frames are stamped before
   the trigger on purpose, so a late clip always looked older than the snapshot that opened the
   window and its push would have been withheld. The rule also misfired for an hour at the
   autumn clock change. Every push that passes novelty is now sent. Limit documented: the card
   shows whichever analysis finished last.
4. **Calmer scenes go to a second card.** A quiet update at a lower human level than the window
   no longer replaces the card of the alert that sounded; it updates a follow-up card
   (`<tag>_more`). At most two cards per camera per window.

Fixed without a decision: tag hashed to stay under the 64-byte APNs collapse-id limit; window
ids unique within a second; a bug in the cooldown code falls back to a plain push; the
unsupported-target notice is a WARNING and the docs note the Sentinel notify-service override;
the option is clamped to 3600 at runtime; the `_last_recognized` slot is gone and the context
is a required argument; the notify service is resolved once per push.

Not done: Russian and Turkish strings for the new field (English fallback).
